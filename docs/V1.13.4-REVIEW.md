# v1.13.4 local review

What this change does: IkevWrt now manages outbound IKEv2 connections only,
including providers such as Windscribe. It bundles Iranian domain rules and
uses Cloudflare exclusively for Tunnel DNS. This build remains local: no source push or release upload was performed.
It was installed and smoke-tested on AX6S/OpenWrt 25.12.6 on 2026-10-30.

The review assumes one AX6S router, a few administrators or open LuCI tabs,
background health checks and 57,559 packaged Iranian domain suffixes.

## Changes

- Removed Inbound Server, VPN Users, their APIs, watcher, ACME integration and
  exported phone/Windows profiles. The three pages are Overview, Outbound
  Tunnel and Policy Routing.
- Removed both manual Update lists buttons. Iran rules are an offline snapshot
  from [Iran-v2ray-rules](../luci-ikev2-domains/iran/SOURCE.md), enabled by default.
  No GeoIP ranges are bundled. Personal additions and existing VPN policies
  remain separate; other optional service lists retain their refresh schedule.
- Fixed Tunnel DNS to `https://cloudflare-dns.com/dns-query`, bootstrapped by
  `1.1.1.1:53` and `1.0.0.1:53`. The UI and backend enforce these values.
  Health checks never switch to another provider. Router DNS and destination
  segment controls remain independent.
- Kept the outbound client, certificate uploads, connection diagnosis,
  per-device rules, routing rollback and fail-closed behavior.

## Upgrade behavior

The upgrade archives the old inbound configuration, credentials and certificate
material locally as `/etc/ikev2-manager/legacy-inbound-backup.tar.gz`, inside
an owner-only directory, with file mode 600. Archive creation is atomic and its
integrity is checked before retirement. Never share this archive: it contains
secrets. The archive is not part of the APK or source tree.

The migration stops the retired watcher, terminates only `ikev2-in`, removes
its generated configuration and owned inbound firewall access, and disables
`ipsec-in` without deleting the live kernel interface. Outbound credentials,
custom outbound profiles, customized outbound zone names and personal policies
are preserved. An applied Site Link exit retains its shared certificate.
Existing external runtime packages and unrelated ACME configuration are kept.

The new policy enables Iran-direct and replaces the previous Tunnel DNS
selection with Cloudflare. It applies the snapshot in both routing engines.
The Iran policy may restart PBR briefly; resolver regeneration can briefly
restart DNS. A failed runtime reconciliation is reported and remains retryable.

## Review findings addressed

1. Reliable mode still required a nonempty Iran CIDR file. It now accepts the
   domains-only snapshot, with a regression that renders the entire list.
2. Standard mode could retain the previous Iran policy after upgrade. Upgrade
   reconciliation now applies the snapshot through the existing routing helper.
3. The old health watcher could recreate inbound settings during migration.
   Packaging replaces it first and stops the migration if that restart fails.
4. A failed archive write could leave a partial recovery file. The archive is
   now published atomically, checked, and covered by a forced-write-failure test.
5. Retiring inbound material could remove a certificate still used by Site Link.
   Migration now honors the existing applied-state ownership contract.

No unresolved must-fix issue was found in the local review. These checks cannot
prove behavior on the router.

## Limits

This version passed the AX6S live checks below. It has not been reboot-tested
or load-tested. Earlier v1.13.3 hardware testing was also limited to Redmi AX6S. The APK
is unsigned; verify the adjacent SHA-256 file before any later installation.

Domain classification needs router DNS. Iran-direct uses DNS-populated WAN
address sets in both engines, so sites sharing an Iranian domain's address can
also bypass the VPN. Reliable mode uses FakeIP for selected VPN domains. A Cloudflare outage can stop tunnel DNS;
there is intentionally no alternate provider.

## Iran-direct priority correction — 2026-10-30

Device full-route rules assigned the VPN mark before PBR evaluated its WAN
address set. PBR then returned immediately for already marked packets, so the
Iran-direct toggle could be enabled and DNS could resolve correctly while
traffic from those devices still went through the VPN.

The Iran PBR include now places its existing WAN-destination check before
that early return, limited to packets carrying the outbound VPN mark. It
uses the actual routing mask and generated WAN mark chain. Other full-route
traffic, FakeIP proxy marks and unrelated packet marks retain their behavior.
No GeoIP ranges or new domain lists were added.

The corrected local v1.13.4 APK was reinstalled on AX6S/OpenWrt 25.12.6. A real
PBR restart regenerated the priority rule exactly once. The full CI suite and
new nondefault-mark/disabled-toggle regression passed. APK privacy scans were
clean. Credential and personal-policy hashes remained unchanged.

Live LAN tests confirmed the reported Iranian sites over WAN and ordinary
full-route traffic over the VPN. The user confirmed that the IP-check site
reports the ISP address and the remaining portal opens in Brave. A plain-HTTP
endpoint on one site independently closed connections over WAN; its HTTPS
endpoint worked. Diagnostic URLs, client addresses and public exit addresses
are kept out of this public record.

Corrected local APK SHA-256:
`5392a639f5dac6d5964fa7dc5aacc47ea64e1f6e2b4b53ef6dedbec23a2fac2c`.

The WAN address set is populated by router DNS. Cached client answers or
browser DNS that bypasses the router can delay classification. Resolved
addresses can be shared by several sites, so a shared address may also take
WAN. No full-router reboot or sustained-load test was performed.
